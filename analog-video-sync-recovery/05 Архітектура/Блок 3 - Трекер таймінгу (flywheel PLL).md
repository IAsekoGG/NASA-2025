# Блок 3 — Трекер таймінгу (flywheel PLL)

**Серце пристрою.** Теорія: [[Flywheel синхронізація]]. Реалізація — прошивка MCU (RP2040 PIO + ядро) або FPGA.

## Мета
На кожен рядок видавати: `t_next` — прогнозований момент початку наступного H-sync (з точністю ≤ 50 нс), `line_no` (0…624/524), `field_parity`, `state ∈ {SEARCH, LOCKED, COAST}`, `input_valid` (чи був у вікні валідний вхідний імпульс).

## Вхід / Вихід
- Вхід: часові мітки фронтів CSYNC (спадних і висхідних — щоб знати ширину імпульсу) з роздільністю 8–16 нс; VSYNC як підказка.
- Вихід: у Блок 4 — `t_next`, `line_no`, `state`; у Блок 5 — режим ключа (PASS / REPLACE / COAST).

## Алгоритм (рівень рядка)
```
кожен фронт з FIFO міток часу:
  width = t_rise - t_fall
  класифікувати: HSYNC (3.5..6 мкс) | EQ (1.5..3.2 мкс) | BROAD (20..32 мкс) | NOISE (інше)
  if state != SEARCH and |t_fall - t_next| > window:  → відкинути (NOISE поза вікном)
  else: err = t_fall - t_next; оновити фазу/період (PI-регулятор), hits++

на кожен передбачений t_next (таймер):
  if не було валідного HSYNC у вікні: misses++, input_valid=false, t_next += period
  line_no = (line_no + 1) mod lines_per_frame
  оновити state:
     SEARCH → LOCKED: hits ≥ 16 поспіль і період у межах 64.0 ± 0.5 мкс (PAL) / 63.56 ± 0.5 (NTSC)
     LOCKED → COAST : misses ≥ 8 поспіль (налаштовується: 4..32)
     COAST  → LOCKED: hits ≥ 8 поспіль у вікні
     COAST  → SEARCH: t_coast > T_max (напр. 5 с) — маховик зупиняється, чекаємо новий сигнал
  параметри: window = ±1.5 мкс (LOCKED/COAST), ±10 мкс (SEARCH); Kp, Ki за таблицею у [[Flywheel синхронізація]]
```
Вертикаль: V-детектор за послідовністю BROAD-імпульсів (≥ 3 з 5 у 2.5 рядках) **у вікні** ±3 рядки навколо очікуваного `line_no = 0`; поза вікном — ігнорувати, поки не буде 2 підтверджень поспіль (захист від хибного «кадру»). Парність — за пів-рядковим зсувом першого BROAD відносно `t_next`.

## Реалізація на RP2040
- PIO SM0/SM1: timestamp обох фронтів CSYNC (техніка Cornell ECE4760), у FIFO → DMA → кільцевий буфер.
- Ядро 1: обробка міток, PLL, автомат станів — ~1000 тактів на рядок з запасу 8000.
- Ядро 0: UART-лог, кнопки, LED, налаштування.
- Прогнозований `t_next` передається у PIO генератора (Блок 4) як **абсолютний час** через спільний 32-бітний лічильник (PIO працюють від одного такту → без дрейфу між капчером і генератором).

## Критерій приймання
- [ ] Симуляція на ПК (Python/C з тими самими функціями): подати запис реальних міток (з логу етапу 0) + синтетичний шум → частка правильно відновлених рядків ≥ 99.9 % при 30 % втрачених/хибних імпульсів.
- [ ] На залізі з чистим сигналом: `|t_next − t_real|` RMS ≤ 30 нс, стан LOCKED безперервно ≥ 10 хв.
- [ ] Вимкнути передавач: перехід у COAST ≤ 1 ms; дрейф `t_next` за 1 с ≤ 60 мкс (кварц 50 ppm) — і **важливо** — після 3 с coasting і повернення сигналу час до LOCKED ≤ 20 ms без «зриву кадру» більше одного разу.
- [ ] Хибні V-sync: подати шум без сигналу — лічильник рядків не повинен «перезапускатися» частіше, ніж раз на T_max.

## Ризики (див. [[Ризики та типові помилки]])
- Обробка в перериваннях із джитером → тільки апаратні мітки та апаратна генерація.
- Занадто вузьке вікно при реальному джитері передавача (дешеві камери мають джитер ±100–200 нс) → зробити ширину вікна адаптивною: 3σ виміряного джитеру, але не менше ±0.5 мкс.
- Період PAL камери ≠ рівно 64.000 мкс (дешеві камери — генератор без кварцу!). Тому інтегральна гілка обов'язкова, і не можна «прибивати» період до константи.
